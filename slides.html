O problema

O lexer decide onde uma palavra termina

texto fonte10_000.00
▶
LEXERregras de token
▶
tokensNUMERIC_LITERAL
▶
parserfora do escopo
  • O lexer corta o texto em tokens e nada mais. Ele não sabe o que é uma consulta válida, só o que é um número, um nome ou uma string.
  • O algoritmo é maximal munch: consome o maior prefixo que alguma regra reconhece, emite o token e recomeça dali.
  • Empate de tamanho é resolvido pela ordem de declaração no arquivo .g4 — quem vem antes vence.
  • Por isso "entrada rejeitada" raramente é uma mensagem de erro: quase sempre é só uma quebra diferente do fluxo de tokens.
Comparamos duas gramáticas do repositório oficial grammars-v4, sem modificar uma linha delas.

Identificador

Uma forma contra quatro formas

GraphQL.g4:445 
NAME : [_A-Za-z] [_0-9A-Za-z]* ;
  • ASCII estrito, uma única forma, sem delimitador.
  • Caixa escrita na mão: [_A-Za-z].
  • query e fragment são NAME válidos — as reservadas moram no parser, não no lexer.
SQLiteLexer.g4:216 
IDENTIFIER:
    '"' (~'"' | '""')* '"'
  | '`' (~'`' | '``')* '`'
  | '[' ~']'* ']'
  | [A-Z_\u007F-\uFFFF] [A-Z_0-9\u007F-\uFFFF]*
;
  • Três formas delimitadas + uma nua; aceita espaço e unicode.
  • caseInsensitive faz [A-Z] casar minúscula: o arquivo engana quem lê rápido.
  • Escape por duplicação ("") — menos na forma [...], que não tem escape nenhum.
Como IDENTIFIER vem depois das ~180 keywords, select vira o token SELECT_, não identificador. Uma coluna chamada select exige delimitador; em GraphQL, um campo query não exige nada.

Número · ANTLR4

10_000.00 separa os dois de forma limpa

SQLiteaceita
10_000.00▶
NUMERIC_LITERAL10_000.00
1 token · 0 erros
GraphQLrejeita
10_000.00▶
INT10 NAME_000 INT0
3 tokens · 1 erro
line 1:6 token recognition error at: '.0'
  • 10 vira INT e para: _ não é dígito. Aí _000 casa NAME, porque underscore inicia identificador em GraphQL.
  • Sobra .00: o ponto sozinho não pertence a token nenhum — PUNCTUATOR só tem '...'.
  • O recover() descarta os dois caracteres reportados e resta 0, um INT.
Um separador de milhar inofensivo produz um fluxo de tokens irreconhecível para o parser.

Texto

Barra invertida contra aspa duplicada

GraphQL.g4:449 
fragment CHARACTER : (ESC | ~ ["\\]) ;
fragment ESC : '\\' (["\\/bfnrt] | UNICODE) ;
fragment UNICODE : 'u' HEX HEX HEX HEX ;

STRING       : '"' CHARACTER* '"' ;
BLOCK_STRING : '"""' .*? '"""' ;
SQLiteLexer.g4:232 
STRING_LITERAL : '\'' ( ~'\'' | '\'\'' )* '\'' ;
Uma linha. Sem escape unicode, sem string multilinha dedicada — e a barra invertida não significa nada.
  • GraphQL exclui dois caracteres do conteúdo livre (~["\\]); SQLite exclui um (~'\'').
  • Só o GraphQL tem \uXXXX. O SQLite não precisa: aceita o caractere acentuado direto.
  • Nas duas, o conjunto complementar casa também \n — string atravessando linha passa no lexer, mesmo quando a spec proíbe.

O desenho denuncia o estilo

  • NAME do GraphQL: um trilho curto. IDENTIFIER do SQLite: quatro diagramas, um por forma aceita.
  • No número a diferença é de estilo: os 8 fragments do GraphQL viram três trilhos curtos apontando pra outros diagramas; a regra inline do SQLite vira um diagrama grande com laços em três níveis.
  • Três ferramentas comparadas: PlantUML (usada aqui), BottleCaps RR e a extensão vscode-antlr4.
  • Nenhum diagrama mostra caseInsensitive nem a ordem de declaração — o desenho de uma regra isolada é sempre uma verdade parcial.

Achados no GraphQL.g4

Três defeitos que o ANTLR não avisa

🚫

ID é inalcançável

ID : STRING ; reconhece a mesma linguagem de STRING e é declarada depois. No empate vence quem vem primeiro — ID nunca é emitido.

💀

fragment EXP é código morto

Ninguém referencia EXP; o expoente real é EXPONENTIAL_PART. Pior: EXP usaria INT, que já traz sinal — 1e--5 passaria por esse caminho.

🐛

UTF8_BOM está errada

'\uEFBBBF' — o ANTLR lê \u com exatamente 4 dígitos. Vira U+EFBB seguido das letras B e F, não o BOM UTF-8.

  • Todos confirmados empiricamente, com entradas dedicadas — não só por leitura do arquivo.
  • O BOM real (U+FEFF) casa por UTF16_BOM, então a regra quebrada é inofensiva na prática: só engana quem lê.
  • No SQLiteLexer.g4, nenhum defeito encontrado.

  • 🧩
    Avaliar um lexer exige ler a sequência de tokens inteira, não procurar mensagem de erro. Os 4 erros saíram todos do GraphQL, que não tem catch-all.
  • 💥
    Erro léxico não fica onde acontece. O recover() descarta um caractere e desloca o resto: em user-profile-name o hífen some e a próxima palavra perde a primeira letra.
  • ✂️
    A fronteira lexer/parser é escolha de projeto. O sinal fica dentro do número em GraphQL e fora em SQLite — as duas decisões estão certas para o que cada linguagem precisa.
